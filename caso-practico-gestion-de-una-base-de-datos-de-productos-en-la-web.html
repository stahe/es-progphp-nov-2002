    7. Caso práctico: gestión de una base de datos de productos en la web

    El código de este caso práctico está disponible |AQUÍ|.

    Objetivos:

    • Escribir una clase para gestionar una base de datos de productos
    • Escribir una aplicación web basada en esta clase
    • Introducir hojas de estilo
    • Proponer una metodología de desarrollo inicial para aplicaciones web sencillas
    • Introducir JavaScript en el navegador del cliente

    Créditos: La esencia de este caso práctico se ha extraído del libro «Les cahiers du programmeur - PHP/MySQL», de Jean-Philippe Leboeuf, publicado por Eyrolles.

    7.1. Introducción

    Un comerciante desea gestionar los artículos que vende en su tienda. Ya dispone de una aplicación de Access en casa que realiza esta tarea, pero le atrae el mundo de la web. Tiene una cuenta con un proveedor de servicios de Internet que permite a sus clientes instalar scripts PHP en sus carpetas personales. Esto les permite crear sitios web dinámicos. Además, estos mismos clientes disponen de una cuenta MySQL que les permite crear tablas para proporcionar datos a sus scripts PHP. Así, el propietario de la tienda tiene una cuenta MySQL con el nombre de usuario «adarticles» y la contraseña «mdparticles». Dispone de una base de datos llamada «darticles» sobre la que tiene derechos de acceso completos. Por lo tanto, nuestro comerciante tiene todo lo necesario para poner en línea su sistema de gestión de productos. Con tu ayuda —ya que tienes conocimientos de desarrollo web— se embarca en esta aventura.

    7.3. Restricciones del proyecto

    El comerciante está migrando una aplicación ACCESS local a una aplicación web. No sabe qué será de ella ni cómo evolucionará. Sin embargo, le gustaría que la nueva aplicación fuera fácil de usar y escalable. Por este motivo, su consultor informático previó, durante el diseño de las tablas, que podría haber:

    • varios usuarios con diferentes permisos: esto permitirá al comerciante delegar ciertas tareas a otros sin concederles derechos administrativos
    • en el futuro, otras tablas además de la tabla ARTICLES

    El mismo consultor hace otras sugerencias:

    • sabe que, en el desarrollo de software, la capa de presentación y la capa de procesamiento deben estar claramente separadas. La arquitectura de una aplicación web suele ser la siguiente:

    La interfaz de usuario aquí es un navegador web, pero también podría ser una aplicación independiente que envía solicitudes HTTP al servicio web a través de la red y formatea los resultados que recibe. La lógica de la aplicación consiste en scripts que procesan las solicitudes de los usuarios, en este caso scripts PHP. La fuente de datos suele ser una base de datos, pero también puede ser un directorio LDAP o un servicio web remoto. Al desarrollador le conviene mantener un alto grado de independencia entre estas tres entidades, de modo que si una de ellas cambia, las otras dos no tengan que cambiar, o solo mínimamente. El consultor informático del comerciante hace entonces las siguientes propuestas:

    • Colocaremos la lógica de negocio de la aplicación en una clase PHP. Así, el bloque [Lógica de aplicación] anterior constará de los siguientes elementos:

    Dentro del bloque [Lógica de la aplicación], podemos distinguir

    • el bloque [IE=Interfaz de entrada], que sirve como punto de entrada de la aplicación. Este permanece igual independientemente del tipo de cliente.
    • el bloque [Clases de negocio], que contiene las clases necesarias para la lógica de la aplicación. Estas son independientes del cliente.
    • el bloque de generadores de páginas de respuesta [IS1 IS2 ... IS=Interfaz de salida]. Cada generador se encarga de dar formato a los resultados proporcionados por la lógica de la aplicación para un tipo de cliente determinado: código HTML para un navegador o un teléfono WAP, código XML para una aplicación independiente, ...

    Este modelo garantiza un alto grado de independencia respecto a los clientes. Tanto si el cliente cambia como si deseamos modificar la forma en que se presentan los resultados, serán los generadores de salida [IS] los que deberán crearse o adaptarse.

    • En una aplicación web, la separación entre la capa de presentación y la capa de lógica de negocio puede mejorarse mediante el uso de hojas de estilo. Estas controlan la presentación de una página web en un navegador. Para cambiar esta presentación, basta con modificar la hoja de estilo asociada. No es necesario alterar la lógica de negocio. Por lo tanto, utilizaremos aquí una hoja de estilo.
    • En el diagrama anterior, la clase de negocio interactuará con la fuente de datos. Suponemos que esta fuente es una base de datos MySQL. Para permitir la migración a otra base de datos, utilizaremos la biblioteca PEAR, que proporciona clases de acceso a bases de datos independientes del tipo de base de datos real. Así, si nuestro comerciante se hace lo suficientemente rico como para instalar un servidor web Microsoft IIS en su empresa, podrá sustituir la base de datos MySQL por SQL Server sin tener que cambiar (o con muy poca necesidad de cambiar) la clase de negocio.

    Comentarios

    • La clase «articles» utiliza la biblioteca PEAR::DB para acceder a la base de datos, de ahí el comando 
    require_once 'DB.php';

    Esta inclusión supone que el script DB.php se encuentra en uno de los directorios especificados en la opción include_path del archivo de configuración de PHP.

    • El generador necesita saber a qué base de datos conectarse y con qué identidad. Esta información se proporciona en el diccionario $dDSN. Recordemos que la suposición inicial era que la base de datos se llamaba dbarticles y pertenecía a un usuario llamado admarticles con la contraseña mdparticles. Tenga en cuenta también que esta aplicación admite múltiples usuarios con diferentes permisos. Aquí hay una ambigüedad que debe resolverse. La conexión se abre efectivamente bajo la identidad de admarticles y, en última instancia, todas las operaciones en la base de datos dbarticles se realizarán bajo esta identidad, ya que es el único nombre reconocido por el SGBD MySQL que tiene privilegios suficientes para gestionar la base de datos dbarticles. Para «simular» la existencia de diferentes usuarios, haremos que el usuario admarticles opere con los permisos del usuario cuyo nombre de usuario ($sUser) y contraseña ($sMdp) se pasen como parámetros al constructor. Así, antes de realizar una operación en la base de datos articles, verificaremos que el usuario ($sUser, $sMdp) tenga los permisos necesarios para hacerlo. Si es así, el usuario admarticles realizará la operación en su nombre.
    • El nombre de usuario y la contraseña del administrador de la base de datos de productos deben pasarse al constructor. Se trata de una precaución acertada. Si estos dos datos estuvieran codificados de forma fija en la clase, cualquier usuario de la clase podría suplantar fácilmente al administrador de la base de datos de productos. De hecho, una clase PHP no está protegida. Por lo tanto, el atributo $bAdmin de la clase —que indica si el usuario ($sUser, $sMdp) para el que estamos trabajando es administrador o no— podría muy bien establecerse directamente desde el exterior, como en el siguiente ejemplo: 
    $oArticles=new articles($dDSN,$sUser,$sMdp)
// ici $sUser a été reconnu comme un utilisateur non administrateur de la base
$oArticle->bAdmin=TRUE;
// maintenant $sUser est devenu administrateur

    PHP no es Java ni C#, y una clase PHP es simplemente una estructura de datos ligeramente más avanzada que un diccionario, pero que no ofrece la seguridad de una clase verdadera en la que el atributo bAdmin se habría declarado como privado o protegido, lo que haría imposible modificarlo desde el exterior. Dado que el usuario de la clase debe conocer el nombre de usuario y la contraseña del administrador de la base de datos de artículos, solo este último puede utilizar la clase. Por lo tanto, la operación anterior ya no le interesa. La clase está ahí únicamente para proporcionarle comodidades de desarrollo. Una consecuencia importante es que no hay necesidad de tomar precauciones de seguridad. Una vez más, quien utilice la clase *articles* es necesariamente el administrador de la base de datos de productos.

    • La clase gestiona los errores de conexión a la base de datos o cualquier otro error de manera uniforme, rellenando el atributo $aErrors con los mensajes de error. Por lo tanto, tras cada operación, el usuario de la clase debe comprobar esta lista.
    • Los métodos addArticle, updateArticle, deleteArticle, selectArticles y execute se derivan directamente del boceto de la interfaz web presentado anteriormente. Se corresponden con las opciones del menú. Los métodos addArticle y modifyArticle se basan en el método verifyArticle para garantizar que el elemento que se va a añadir o modificar contenga datos correctos. Del mismo modo, el método existsArticle garantiza que no estamos a punto de añadir un artículo que ya existe. Podríamos prescindir de este método si utilizáramos una tabla de artículos en la que el código fuera la clave principal. En ese caso, el propio SGBD señalaría el error de la adición debido a un duplicado. Probablemente lo haría con un mensaje de error difícil de leer y en inglés.
    • Un elemento que se va a modificar o eliminar se identificará por su código único. El método `getCodes` recupera todos estos códigos.
    • El método disconnect cierra la conexión con la base de datos, que se abrió al crear el objeto. No vemos aquí la utilidad del método connect, que restablecería una conexión con la base de datos. Esto nos permite abrir y cerrar esta conexión a voluntad utilizando el mismo objeto. La ventaja solo se hace evidente cuando se utiliza junto con la aplicación web. La aplicación creará un objeto «items» y lo almacenará en una sesión. Aunque la sesión podrá conservar la mayoría de los atributos del objeto a lo largo de sucesivos intercambios cliente-servidor, no puede conservar el atributo que representa la conexión abierta. Por lo tanto, esta conexión debe reabrirse con cada nuevo intercambio cliente-servidor. Solicitaremos una conexión persistente para que la conexión abierta se almacene en un grupo de conexiones y permanezca abierta de forma permanente. Así, cuando el script solicite una nueva conexión, esta se recuperará del grupo de conexiones. De este modo, conseguimos el mismo resultado que si la sesión hubiera podido almacenar la conexión abierta.
    • El método `existeUser` permite al constructor determinar si el usuario `$sUser`, identificado por la contraseña `$sMdp`, existe realmente. Si es así, el método comprueba si el usuario es administrador (tal y como se indica en la tabla `USERS`) y almacena esta información en el atributo `$bAdmin`. Si no es administrador, el método recupera sus permisos de la tabla DROITS y los almacena en el atributo $dDroits, que es un diccionario de doble índice: $dDroits[$table][$permission] es «y» si el usuario $sUser tiene el permiso $permission en la tabla $table y «n» en caso contrario.

    Escribe la clase de artículos. El acceso a la base de datos se gestionará mediante la biblioteca PEAR::DB, que te permite trabajar independientemente del tipo exacto de base de datos.

    7.5.2. Proceso típico de una solicitud del cliente

    El cliente interactúa con la aplicación a través de los enlaces del área 2 de la página de la plantilla. Estos enlaces serán del siguiente tipo:

    apparticles.php?action=xx&phase=y&PHPSESSID=zzzzzzzzzzzz

    action
    se refiere a la acción actual de entre las siguientes:
    autenticar
    autenticación del cliente
    seleccionar artículos
    seleccionar elementos (ver)
    actualizar artículo
    actualizar un elemento
    eliminar artículo
    eliminar un artículo
    SQL
    ejecutar cualquier consulta SQL (administrador)
    fase
    una acción se puede realizar en varios pasos; se refiere al paso actual
    PHPSESSID
    token de sesión una vez iniciada la sesión; permite al servidor recuperar la información almacenada en la sesión durante intercambios anteriores

    Del mismo modo, el atributo «action» de los formularios tendrá el mismo formato. Por ejemplo, en la página de inicio hay un formulario de inicio de sesión en la sección 4. La etiqueta HTML de este formulario se define de la siguiente manera:

    <form name="frmLogin" method="post" action="apparticles.php?action=authentifier&phase=1">

    La solicitud del cliente es procesada por el script principal de la aplicación, llamado apparticles.php. Su función es construir la respuesta para el cliente. Siempre procederá de la misma manera:

    • En función del nombre de la acción y de la fase actual, reenviará la solicitud a una función especializada. Esta función procesará la solicitud y generará la página de respuesta adecuada. Para cada solicitud del cliente, puede haber varias páginas de respuesta posibles: página1, página2, ..., páginaN. Estas páginas contienen información que debe ser calculada por la función. Por lo tanto, son páginas parametrizadas. Serán generadas por los scripts página1.php, página2.php, ..., páginaN.php.
    • En aras de la coherencia, las partes variables de las páginas que se mostrarán en la zona 4 de la página de plantilla también se colocarán en el diccionario $main.

    Supongamos que, en respuesta a una solicitud, el servidor debe enviar la página pagex.php al cliente. Procederá de la siguiente manera:

    • Colocará los valores necesarios para la página pagex.php en el diccionario $main
    • establecerá $main['content'], que especifica la URL de la página que se mostrará en la zona 4 de la página de plantilla, con la URL de pagex.php
    • solicitará la visualización de la página de plantilla con la instrucción 
    include "main.php";

    7.5.5. El módulo de entrada de la aplicación

    Los clientes solo conocerán el módulo de entrada de la aplicación: apparticles.php. El esquema general de su funcionamiento es el siguiente:

    • Se recupera y analiza la solicitud del cliente. Puede estar parametrizada o no. Cuando está parametrizada, los parámetros esperados son los siguientes: action=[action]&phase=[phase]&PHPSESSID=[PHPSESSID]
    • Si la solicitud no está parametrizada o si los parámetros recuperados no coinciden con los esperados, el servidor responde enviando la página de autenticación (nombre de usuario, contraseña). Una vez que el usuario ha iniciado sesión correctamente, se crea una sesión. Esta sesión se utilizará para almacenar información a lo largo de las interacciones cliente-servidor.
    • Si una solicitud se reconoce correctamente, es procesada por un módulo que depende tanto de la acción como de la fase actual.
    • Todo el acceso a la base de datos se gestiona a través de la clase de negocio articles.php.
    • El procesamiento de una solicitud siempre finaliza enviando la página main.php al cliente, en la que se ha especificado en $main['content'] la URL de la página que se colocará en la zona 4 de la página de plantilla.

    7.7.2. Mejora de la seguridad

    Al desarrollar una aplicación web, nunca debe dar por sentado que el cliente es un navegador y que la solicitud que envía está controlada por el formulario que le envió antes de dicha solicitud. Cualquier programa puede actuar como cliente de una aplicación web y, por lo tanto, enviar cualquier solicitud —ya sea parametrizada o no— a la aplicación. Por lo tanto, la aplicación debe verificarlo todo.

    Si observamos el código del script apparticles.php, vemos

    • que no puede tener lugar ninguna acción, salvo la autenticación, sin una sesión. Una sesión solo existe si el usuario se ha autenticado correctamente. Recordemos que una sesión se identifica mediante una cadena de caracteres bastante larga llamada token de sesión, que tiene la siguiente forma: 176a43609572907333118333edf6d1fb. Este token se puede enviar a la aplicación de diversas formas, por ejemplo, utilizando una URL parametrizada: 
    
apparticles.php?PHPSESSID=176a43609572907333118333edf6d1fb.

    Un programa que solicitara repetidamente la URL anterior mientras variara aleatoriamente el token con la esperanza de encontrar el correcto probablemente tardaría muchos días en generar la combinación correcta, dada la enorme cantidad de combinaciones posibles. Para entonces, dado que la sesión tiene una duración limitada, lo más probable es que haya caducado. Otro riesgo es que el token, transmitido en texto plano a través de la red, pudiera ser interceptado. Se trata de un riesgo real. Por lo tanto, se puede utilizar una conexión cifrada entre el servidor y su cliente.

    • Una vez iniciada la sesión, solo se permiten determinadas acciones. Una URL configurada como action=cheat&phase=0&PHPSESSID=[PHPSESSID] sería rechazada porque la acción «cheat» no es una acción autorizada. Cuando los parámetros (action, phase) no se reconocen, nuestra aplicación responde con la página de autenticación.

    Sin embargo, la aplicación no verifica si las acciones autorizadas siguen la secuencia correcta. Por ejemplo, las dos acciones siguientes:

    1. action=addArticle&phase=0&PHPSESSID=[PHPSESSID]
    2. action=updateArticle&phase=1&PHPSESSID=[PHPSESSID]

    son dos acciones autorizadas. Sin embargo, la acción 2 no está autorizada a seguir a la acción 1.

    ¿Cómo podemos rastrear la secuencia de URL solicitadas por el navegador del cliente?

    Podemos utilizar dos variables PHP: $_SERVER['REQUEST_URI'] y $_SERVER['HTTP_REFERER'], que son dos datos enviados por los navegadores de los clientes en sus encabezados HTTP.

    $_SERVER['REQUEST_URI']: Es la URI solicitada por el cliente. Por ejemplo

    /apparticles.php?action=addArticle&phase=0&PHPSESSID=[PHPSESSID]

    $_SERVER['HTTP_REFERER']: Se trata de la URL que se mostraba en el navegador antes de la nueva URL que el navegador está solicitando en ese momento (la URI anterior). Por ejemplo, si el navegador que mostraba la URI mencionada anteriormente realiza una nueva solicitud a un servidor, la variable $_SERVER['HTTP_REFERER'] para esa solicitud tendrá el valor 

    http://machine:port//apparticles.php?action=addArticle&phase=0&PHPSESSID=[PHPSESSID]

    Para verificar que dos acciones de nuestra aplicación se suceden en orden, podemos proceder de la siguiente manera:

    Durante la acción 1:

    • anotamos el URI solicitado (URI1) y lo guardamos en la sesión

    Durante la acción 2:

    • recuperamos el HTTP-REFERER de la acción 2. A partir de ahí, obtenemos el URI (URI2) de la URL que se mostraba anteriormente en el navegador que realizó la solicitud.
    • Recuperamos el URI (URI1) que se almacenó en la sesión, que es el URI de la acción solicitada previamente al servidor
    • Si la acción 2 sigue a la acción 1, entonces URI2 debe ser igual a URI1. Si no es así, rechazaríamos realizar la acción solicitada y mostraríamos la página de autenticación.
    • Almacenamos el URI URI2 de la acción actual en la sesión para la verificación de la siguiente acción. Y así sucesivamente.

    He aquí un ejemplo. Tras la autenticación, hacemos clic en el enlace [Añadir un artículo]:

    La URL de esta página es:

    http://localhost:81/st/php/articles/gestion/articles8/apparticles.php?action=addArticle&phase=0&PHPSESSID=006a63e6027f16c70b63cdae93405eeb

    Directamente en el campo [Dirección] del navegador, modificamos la URL de la siguiente manera:

    http://localhost:81/st/php/articles/gestion/articles8/apparticles.php?action=deleteArticle&phase=1&PHPSESSID=006a63e6027f16c70b63cdae93405eeb

    A continuación, aparece la página de autenticación:

    Esto merece una explicación. Cuando se solicita una URL escribiéndola directamente en la barra de direcciones del navegador, este no envía el encabezado HTTP_REFERER. Por lo tanto, nuestra aplicación no puede encontrar el URI de la acción anterior, que había almacenado en la sesión. A continuación, devuelve la página de autenticación como respuesta.

    Este mecanismo funciona bien para los navegadores web, pero no para un cliente programado. Un cliente programado puede enviar el encabezado HTTP_REFERER que desee. Por lo tanto, puede «engañar» afirmando que ha pasado por un determinado paso cuando en realidad no lo ha hecho. Por lo tanto, debe asegurarse de que se siga la secuencia de pasos. Así, si la acción solicitada es action=addArticle&phase=1 (entrada), entonces la acción anterior debe ser necesariamente action=deleteArticle&phase=0 (solicitud inicial de la página de entrada) o action=addArticle&phase=2 (retorno a la entrada tras una adición incorrecta). Del mismo modo, si la acción solicitada es action=addArticle&phase=2 (añadir), entonces la acción anterior debe ser action=addArticle&phase=1 (entrada). Podemos obligar al usuario a seguir estas secuencias.

    7.7.4. Mejora del rendimiento

    Por ahora, hemos optado por un navegador de cliente ligero: no hace más que mostrar contenido. Podemos hacer que realice procesamientos incluyendo scripts en las páginas web que le enviamos. Estos pueden estar escritos en varios lenguajes, en particular VBScript y JavaScript. Internet Explorer y Netscape dominan el mercado de los navegadores en una proporción de aproximadamente 60/40. Además, IE solo está disponible en Windows y no en Unix, por ejemplo, donde predomina Netscape. Netscape no ejecuta VBScript de forma nativa, mientras que ambos navegadores ejecutan JavaScript. Dado que Netscape sigue teniendo una cuota significativa del mercado de los navegadores, se debe evitar el uso de VBScript. Por lo tanto, JavaScript se utiliza generalmente en los scripts del lado del cliente.

    Las tareas de procesamiento que no requieren la intervención del servidor se delegan a los scripts del lado del cliente. En nuestra aplicación, sería conveniente que el navegador del cliente enviara una solicitud al servidor solo después de verificarla. Por lo tanto, no tiene sentido enviar una solicitud de autenticación al servidor si el usuario ha dejado en blanco el campo [login] del formulario de autenticación. Es preferible notificar al usuario que su solicitud no es válida:

    Tenga en cuenta que esto no impedirá que el servidor verifique que el campo de inicio de sesión no esté vacío, ya que el cliente no es necesariamente un navegador y es posible que no se haya realizado la verificación previa. Suponer que el cliente es un navegador supone un riesgo de seguridad importante para la aplicación.

    7.8. Lecturas recomendadas

    Para concluir, aquí hay algunas ideas para ampliar este estudio de caso:

    • Sería interesante ver si la página estándar de esta aplicación podría convertirse en una clase. Esta clase podría utilizarse entonces en otras aplicaciones.
    • Nuestra aplicación es muy adecuada para clientes basados en navegador, pero no tanto para clientes de «aplicaciones independientes». Estos deben:
      • establecer una conexión TCP con el servidor
      • «comunicarse» con él a través de HTTP
      • analizar sus respuestas HTML para encontrar la información deseada, ya que es probable que el cliente independiente no esté interesado en el código HTML de presentación destinado a los navegadores.

    Sería conveniente que nuestra aplicación generara XML en lugar de HTML. De este modo, sus clientes podrían ser tanto navegadores (al menos los más recientes) como aplicaciones independientes. Estas últimas no tendrían ningún problema para encontrar la información que buscan, ya que la respuesta XML del servidor no contendría información de presentación, sino únicamente contenido.

    • Sin duda, tendríamos que abordar el acceso simultáneo a la base de datos de artículos. Hay al menos dos puntos que aclarar:
    1. ¿Gestiona correctamente el SGBD utilizado por la aplicación el acceso simultáneo al mismo artículo? Por ejemplo, ¿qué ocurre si dos usuarios editan el mismo artículo al mismo tiempo (hacen clic en el botón [Editar] simultáneamente)? Probablemente esto dependa del SGBD subyacente.
    2. Actualmente, nuestra aplicación no gestiona el acceso concurrente. Sin embargo, la base de datos debería permanecer en un estado coherente, incluso si cabe esperar algún comportamiento inesperado. Consideremos la siguiente secuencia de eventos:
        • El usuario U1 comienza a editar un artículo
        • El usuario U2 comienza a eliminar el mismo artículo poco después
        • Cada una de estas acciones requiere comunicación cliente-servidor. Dependiendo de cómo trabaje cada usuario, el usuario U2 puede terminar su tarea antes que U1. Cuando U1 termine sus ediciones y haga clic en [Editar] para guardarlas, verá la página de información como respuesta, con el SGBD indicando que [se modificaron 0 filas], porque la página que pretendía editar fue eliminada mientras tanto. Es probable que el usuario se sorprenda. Desde el punto de vista de la usabilidad, probablemente sería mejor mostrar una página que indicara el error con mayor claridad. Además, se podría considerar conceder al usuario acceso exclusivo a un artículo tan pronto como comience a actualizarlo. Si otro usuario intentara editar el mismo artículo, se le informaría de que ya hay otra edición en curso. Esto supondrá un problema si el primer usuario tarda en guardar sus cambios: los demás quedarán bloqueados. Es necesario encontrar soluciones para esto, y estas dependerán en gran medida de las capacidades del SGBD que se utilice. Oracle, por ejemplo, tiene mayores capacidades en este ámbito que MySQL.
